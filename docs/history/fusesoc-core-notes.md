# FuseSoC `.core` files: what they already solve (spike10, 2026-11-22)

> Historical note, copied from `sysmlpy_spike` at the move (2026-11-25). Paths
> refer to that repository; the maintained code is in `src/hdl_architect/`.

Tried with fusesoc 2.4.6 (pinned in the venv) on a scratch copy of FpgaOne's
HDL: six hand-written CAPI2 `.core` files (uart, serial_csr, device_csr,
the AXI crossbar as vendor IP, serial_subsystem, fpga_one).

## What happened

- `fusesoc --cores-root ws core list` found all six by searching the folder
  tree: **where a core sits does not matter**, only its name.
- `fusesoc run --target sim --build internal:fpga_one:fpga_one` (GHDL)
  resolved the dependencies, copied the sources into a build tree, created one
  VHDL library per core (`logical_name`) and compiled them in dependency order:
  device_csr, serial_csr, uart, serial_subsystem, fpga_one (the same order as
  our `compile.do`).
- The crossbar's `.xci` (file type `xci`) is passed to Vivado targets and
  ignored, with a warning, for GHDL.
- Edalize warns that the tool API it uses for GHDL is deprecated in favour of
  its flow API.

## What a core holds (CAPI2 top-level keys)

`name` (VLNV: vendor:library:name:version), `description`, `license`,
`filesets` (files, file types, VHDL `logical_name`, `depend` on other cores
by name), `targets` (sim / synth / lint: tool, toplevel, tool options),
`parameters`, `generate` / `generators` (files produced by a tool, e.g. IP),
`scripts`, `provider` (fetch the core from git, GitHub, SVN, a URL), `virtual`
(this core implements an abstract core: several implementations of one
interface), `mapping`, `vpi`.

Libraries of cores are registered in `fusesoc.conf` (`fusesoc library add`)
with a sync type: local, git, SVN.

## How it lines up with what we were about to invent

| We needed | FuseSoC has |
|---|---|
| per-block file list | a core's filesets |
| the block's VHDL library | `logical_name` |
| external IP from git or SVN | libraries with sync type git/SVN, or a core's `provider` |
| "where the block lives" | nowhere: cores are found by name under the cores roots |
| vendor IP regenerated by Vivado | `xci` files, `generate`/generators |
| compile order | dependencies between cores |
| SBOM-type facts | VLNV (vendor, version), `license` |
| one interface, several implementations | `virtual` cores |

So the **workspace map shrinks** to: which core implements each model
definition (by VLNV), plus the template rules the scaffolder uses to place a
*new* block's folder and name its core. Folders of existing blocks need no
mapping at all.

## Questions this raises

1. `@HdlSource` (library, files) and `@IpConfig` (VLNV, .xci) in `layered/`'s
   model would move to the cores; `@Provenance` could too (VLNV + `license`).
2. CLAUDE.md says `.core` files are "generated from the IR, never
   hand-written". That holds for cores the scaffolder creates (containers, new
   blocks), not for a designer's leaf core or an external IP's own core.
3. Edalize's GHDL backend is deprecated in favour of the flow API: use the
   flow API if we adopt it.
